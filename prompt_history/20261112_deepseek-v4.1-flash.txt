## 結論

企画は良い。ただし価値の中心は「整形」ではなく **「これは何か／何が問題か」を日本語一文で言い切る部分** です。整形はその根拠の提示。ここを設計の中心に据えると、他が全部きれいに決まります。

一番危ないのは **ルールが複数一致したときの合成**（20個のルールは1入力に5個くらい当たる）。ここを設計しないと、あとから直せなくなります。

---

## 1. ルールを3種類に分ける（最重要）

「AWS WAF 的」は比喩として半分正しくて、半分違います。WAF は全ルールが独立に **1つの判定（許可/拒否）** に寄与しますが、ここは各ルールが **変換** を返すので、合成すると壊れます（base64解除 → JSON整形 → さらに… の無限連鎖）。

推奨は役割で3層に割ることです。

| 層 | 役割 | 例 | 動作 |
|---|---|---|---|
| **Wrapper（剥がす）** | デコード | base64 / URLエンコード / hex dump / unicode escape | 出力を新しい入力として**再判定に戻す**（深さ上限3） |
| **Classifier（見分ける）** | 形式判定 | JWT / JSON / XML / メール / ログ / 証明書 / 画像 | 整形・可視化して**主結果**を出す |
| **Annotator（注釈する）** | 全入力に付く | 統計 / エラー抽出 / マスキング / 機種依存文字 | **全ルール並列で走る**（出力は変えない） |

これで「複数一致」の大半は消えます。base64 の画像は「wrapper→classifier(画像)」の1本道になり、JWT は「JSON でもある」ではなく「JWT という型の JSON」として1つに決まります。

## 2. 優先順位は「順位」より「主役1つ＋他の解釈」

`priority: number` だけだと、同点時の挙動が説明できません。推奨：

- 判定は **スコア＋根拠** で持つ。固有シグネチャ（JWT の `eyJ` + 3分割 + `alg`）は決定的に強く、統計系（「タブが多い＝TSV」）は弱く。
- **主結果は1つ**だけ全面表示。他の一致は「他の解釈（3件）」として下に並べ、クリックで切替。
- 非エンジニアに5枚タブを見せると詰む。「JSON と CSV の両方に見えます」は **1行で言う**（例：*「タブ区切りに見えますが、JSONとしても読めます」*）。
- 信頼度を必ず出す（高/中/低＋理由）。**低のときは自動変換しない**（「可能性」として提示のみ）。誤変換は、変換しないより罪が重い。

## 3. ルール定義は「宣言的 manifest ＋ 必要ならコード」

「script でルール定義」は正解ですが、全部コードにすると設定として読めなくなります。ハイブリッドを推奨。

```ts
type Rule = {
  id: string;                       // 'jwt', 'log.http'
  layer: 'wrapper' | 'classifier' | 'annotator';
  label: string;                    // 画面に出る日本語名
  appliesTo: 'text' | 'image' | 'both';
  detect(ctx: Ctx): Match | null;   // { score, evidence[], headline }
  transform?(ctx: Ctx, m: Match): Result;  // 省略可（wrapper/classifierのみ）
  fixtures: { name: string; input: string; expect: Partial<Match> }[];
};
```

- `src/rules/*.ts` を `import.meta.glob` で自動登録 → **ルール追加＝ファイル追加**で完結（ルールセット分離の要件を満たす）
- 宣言だけで足りるものは `detect` を書かず `signatures: [...]` だけの DSL にフォールバック
- **各ルールにフィクスチャ必須**（`npm test` で input→期待判定を検証）。判定ツールの品質はここでしか守れません。20ルール×数件を最初から持つべき。

## 4. 「英語→日本語」は翻訳ではなく **エラー辞書** にすべき

ここは明確に方針を変えたほうがいいです。ブラウザ内 MT（Bergamot 等）は 15〜20MB のモデルで、技術エラーの訳文品質が実用に届きません。そして何より、**非エンジニアが欲しいのは訳文ではなく「原因と次にやること」**です。

推奨：`パターン → { 一言解説, よくある原因, 次にやること }` の辞書。

| 入力 | 出すもの |
|---|---|
| `HTTP 502` | ゲートウェイが応答できない。上流サーバの停止/タイムアウトが典型。まず再読み込み、次に管理者へ |
| `SMTP 550 5.7.1` | 送信を拒否された（迷惑メール判定/中継拒否）。添付とリンクを外して再送 |
| `SSL_ERROR_RX_RECORD_TOO_LONG` | HTTPS のはずが HTTP で応答している。URL の `https` を疑う |
| `ENOENT: no such file or directory` | ファイル/フォルダが存在しない（パスの打ち間違い） |

- 未知パターンは **無理に訳さない**：「辞書にないエラーです。原文をそのまま表示」＋コピー。中途半端な訳は誤誘導になります。
- ラベルも「翻訳」ではなく **「エラーの意味」** に。オプションの「日本語に翻訳」は、この辞書を全文に適用するかどうかのスイッチに統合するのが自然です（ルール16とオプション2が重複しているので統合）。

## 5. PDF は `window.print()` 一択（日本語フォント問題）

jsPDF＋日本語フォントは 10MB 級の埋め込みが必要で、html2canvas はラスタライズで文字が汚く、選択もできません。

- Markdown を **サニタイズした HTML** にし、印刷用 CSS（`@page`）で `window.print()` → 「PDF に保存」
- 副産物として **「サポート用レポート」** を強く推奨：判定結果＋統計＋マスク済みデータ＋入力の SHA-256＋ツールのバージョンを1枚に。問い合わせ整理に効くし、これが「非エンジニア向けツール」の差別化になります。
- 「PDF ボタンはルール一致時のみ」は自然に実装できます（レンダリング可能ルールが主結果のときだけ表示）。

## 6. 「無通信」を仕様ではなく **検証可能な仕組み** にする

CSP は表明であって証明ではありません。三点セットを推奨。

1. **CSP（本番のみ）**：`default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data: blob:; font-src 'self'; worker-src 'self'; connect-src 'none'; form-action 'none'; base-uri 'none'; frame-ancestors 'none'`
   - `worker-src blob:` は使わない（Worker は self 配信のファイルに統一）→ より強い
   - `report-uri` は **入れない**（レポート自体が通信）
   - dev では HMR のため `ws:` が必要 → **ビルド時のみヘッダ付与**（CloudFront）にし、index.html には入れない
2. **CI ゲート**：`dist/` を grep して `fetch(|XMLHttpRequest|WebSocket|sendBeacon|http://|https://` の外部 URL を検出したらビルド失敗
3. **E2E 検査**：Playwright で全リクエストを記録し、same-origin 以外ゼロをアサート。README に「この検査で担保」と書ける

加えて **Service Worker で完全オフライン動作**（一度読み込めば機内/閉域でも動く）。「ネットに繋がっていない状態でも使える」は、非エンジニアに一番伝わる無通信の証拠になります。

## 落とし穴（先に潰しておくもの）

| 領域 | 危険 | 対策 |
|---|---|---|
| Markdown/HTML 表示 | `<script>` や `onerror` 入りマークダウン＝XSS（CSP で実行は止まるが、`<img src>` は飛ぶ） | 生 HTML を除去、リンクは無効化、表示はサンドボックス iframe（`allow-scripts` なし） |
| SVG 画像 | `<img src=blob:svg>` でスクリプト実行 | SVG は**テキスト扱い**。画像として描画しない |
| 巨大入力 | 数MBログで画面フリーズ | 入力上限＋超過時は先頭N行＋「全文をTSVでDL」導線。重処理は段階的 async |
| ネスト base64 | 展開爆発 | 深さ3・出力上限（例 8MB）・総デコード回数上限 |
| JSON 整形 | 64bit 超の数値IDが壊れる（`JSON.parse` で精度落ち） | 数値リテラルを**文字列として保持**するトークナイザ実装。少なくとも警告を出す |
| CSV/TSV → Excel | CP932 問題。UTF-8 のままだと文字化け | クリップボードは UTF-8 TSV、**ダウンロードは UTF-8 BOM 付き**。CP932 出力は「要望があれば」（変換表が要る） |
| 文字化け復元 | UTF-8 を CP932 として読んだ型は復元可、逆（`�`）は不可 | `TextDecoder('shift_jis')` で**片方向のみ対応**と明記。復元可/不可を判定して表示 |
| HEIC | iPhone 写真がドロップされる | `heic2any` を遅延ロード（rm と同じ）。非対応時は「設定で JPEG に」案内 |
| Cookie / ローカル保存 | 貼った秘密情報が残る | **保存しない**（reload で消える）を既定に。設定も sessionStorage のみ |
| 共有 URL | `?data=` で漏れる | 入力の URL 埋め込みは**実装しない** |
| 空振り | 何も当たらない | 必ず「判定できませんでした」＋上位3候補＋統計だけ出す（無言で真っ白にしない） |

**マスキング**は方針に賛成。追加提案：
- Luhn チェックでクレカ誤検知を落とす、マイナンバーはチェックディジット、住所は「都道府県＋市区町村＋丁目」に限定（誤検知が多く非エンジニアの信頼を壊す）
- 既定は **OFF**、ただし検出時に「機密らしきもの N 件」バナーを出す（勝手に隠すと「壊れた」と誤解される）
- マスクは**コピー/PDF/TSV すべてに一貫適用**、原文は1件ずつだけ開ける

## スコープ提案

「ルール=辞書データ＋フィクスチャ」なので、1ルールあたりの実コストは見た目より高い。区切るのが賢明です。

| 版 | ルール | 理由 |
|---|---|---|
| **v1** | ①JSON/XML/コード整形＋**構文エラー位置** ②ログ→TSV＋HTTP/SMTPエラー抽出 ③エラー辞書 ④base64/URL/hex 再帰デコード ⑤JWT ⑥画像（EXIF/GPS）＋QR/バーコード | IT トラブル対応の実発生頻度が高い順。①〜④は相互依存が強く、一緒に作ると綺麗に収まる |
| **v1.5** | メールソース、証明書/鍵（DER パーサは自前 300 行程度で済む）、日時/GMT、Cookie、文字化け、ハッシュ推定 | 単価は低いが件数が多く、辞書が育つ領域 |
| **v2** | Markdown→PDF、暗号化バイナリ推定、機種依存文字の網羅 | PDF は印刷 CSS の作り込みが要る。推定系は表現の慎重さが要る |

推定系（ハッシュ種別・暗号化・鍵）は **「推定」と明記＋候補を併記**。16進32桁を見て「MD5 です」と言い切るのは、非エンジニア相手だと事故になります（「SHA-256 の先頭32桁」も同型）。

## 結論

**未登録なら実害はほぼありません。** ただし「secret が漏れた」こと自体は事実なので、**IAM に残っている未割り当て（Unassigned）の MFA デバイスを削除**してください。5分で終わります。

## なぜ「ほぼ大丈夫」なのか

TOTP の QR に入っている `secret` は「種（シード）」です。6桁コードはこの種から計算できますが、**AWS 側でデバイスが未割り当てのままなら、そのコードはログインに使えません**。

- 割り当て（EnableMFADevice）を完了するには、**すでにログイン済みで MFA を通過した権限者**が操作する必要があります
- つまり「secret を知っているだけ」では、あなたのアカウントにログインできません
- 危険になるのは、**そのデバイスが実際に割り当てられていた場合**、または同じ secret を別のサービスで使い回した場合です

## ただし漏れているのは secret だけではない

QR のラベルには次の情報も入っていました。

| 漏れた情報 | 性質 |
|---|---|
| `secret=...` | 認証情報（未割り当てなら無効） |
| `REDACTED` | AWS アカウントID（**秘密ではない**が、公開は避けたい） |
| `test1` | IAM ユーザー名 |

アカウントID＋ユーザー名は、標的型の連絡（「AWSのサポートです」等）に使われることがあります。**単体では乗っ取りには使えません**が、公開しない方がよい情報です。

## 1. GMT / UTC を日本時間に変換

`parseDateTime()` を追加し、よくある表記をまとめて JST にします（HTML で `<time>` を出す代わりに、表・要点欄を日本時間に）。

| 場所 | before | after |
|---|---|---|
| メールの Date | `Thu, 12 Nov 2026 22:55:01 +0900` | **2026年11月12日(木) 22:55:01 JST**（元の表記は注記） |
| Cookie の Expires | `Wed, 12 Nov 2026 10:00:00 GMT` | **2026年11月12日(木) 19:00:00 JST** |
| アクセスログの日時 | `12/Nov/2026:10:00:00 +0900` | **2026年11月12日(木) 10:00:00 JST** |
| CloudFront（UTC） | `2026-11-12 10:00:00` | **19:00:00 JST**（UTC として解釈） |
| syslog | `Nov 12 10:00:00` | **2026年11月12日(木) 10:00:00 JST**（年は今年・JST とみなす） |
| Apache error log | `Wed Oct 11 14:32:52 2000` | **JST** |

対応した形式：RFC1123（GMT/UTC/+0900）、Apache access、asctime、ISO8601（Z / オフセット / なし）、CloudFront、EXIF、日本式、syslog。

```markdown
> スクリプト（&lt;script&gt;）と外部の画像は表示しません。…
```

プレビューでは `スクリプト（<script>）` と正しく表示され、以降の本文も切れません。

あわせて、次のフィールドも同様にエスケープしました（データに `<` `>` `&` が入っても壊れないように）。

| 箇所 | 対応 |

| 表の注記 | `escHtml` |

## なぜ「署名」は不適切か

| 用語 | 実際の意味 | 今回の SHA-256 |
|---|---|---|
| **署名（signature）** | **秘密鍵**で作る。公開鍵で検証でき、**「誰が作ったか」「改ざんされていないか」**を証明する | ✗ 作れない（鍵が必要） |
| **ハッシュ／指紋（fingerprint）** | 内容から計算する固定長の値。**「同じ内容か」**を確かめる | ✓ これ |

「署名」と呼ぶと、**本人確認・真正性の保証**に受け取られます。これは非エンジニア相手だと特に危険で、「署名だから本物だ」と誤解させてしまいます。実際、このアプリの JWT の説明でも「**署名は確認していません**」と書いているので、同じ画面で2種類の「署名」が混ざるのも避けたいところです。

## 採用した表記

**「SHA-256（内容の照合値）」** に変更しました（本番反映済み）。

> 同じ内容かどうかを確かめる値（指紋のようなもの）です。本人確認のための「署名」ではありません。「入力がハッシュ値かどうか」は、上の判定（ハッシュ値）で調べています

- 「照合」はビジネスでも通じる言葉で、用途（突き合わせ）が伝わります
- 補足で「指紋のようなもの」と添えたので、直感的にも分かります
- 「署名ではない」と明示して、誤解の余地をなくしました
